# Changelog vs. оригинального репозитория

## 🆕 v2.1 — доработка «Сделать ведомым» + чистка общего списка от чужих групп

- **«👑 Назначить ведущим»: общий список кандидатов больше не включает
  чужие группы.** Раньше туда попадали и ведомые ДРУГИХ ведущих (можно
  было случайно «переподключить» чужого ведомого прямо из общего списка,
  что засоряло список и создавало риск случайного переподключения).
  Теперь `_eligible_candidates()` показывает только реально свободных
  пользователей + собственных текущих ведомых этого ведущего (чтобы они
  по-прежнему были предотмечены и их можно было снять). Если правда нужно
  переподключить кого-то от одного ведущего к другому — сначала отвязать
  через «💔 Разгруппировать» у старого, дальше он появится как свободный.
- **«🔗 Сделать ведомым» теперь двухрежимный.** Сначала — список
  существующих ведущих (как раньше). Кнопка **«📋 Показать всех
  свободных»** переключает на список тех, кто пока не ведущий и не
  ведомый — выбор там делает этого человека ведущим впервые, не выходя из
  текущего экрана. Обратная кнопка «👑 Показать только ведущих» возвращает
  назад. Если в базе вообще нет ни одного ведущего — экран сразу
  открывается в режиме «свободные», без лишнего шага.
- **`core/db.py`**: новая `get_unlinked_users()` — пользователи, которые
  не ведущие и не ведомые (используется и в списке «свободных» для
  реверс-флоу).

## 🆕 v2.0 — прямой чат с клиентом + смена направления сортировки

- **«💬 Открыть чат в Telegram»** — новая кнопка в карточке пользователя
  (только если у него привязан `telegram_id`). Это deep-link
  `tg://user?id=...`, который открывает настоящий 1:1-чат с этим
  Telegram-аккаунтом в приложении — не через бота (в отличие от «✉️
  Написать», которая шлёт сообщение через бота), а напрямую.
- **Новая кнопка-переключатель направления сортировки** в «⚙️ Сортировка
  БД»: **«⏳ Сначала истекающие»** ↔ **«♾ Сначала безлимитные/дальние»**.
  По умолчанию — как раньше (безлимитные и с дальней датой сверху).
  Во втором режиме порядок переворачивается: ближайшие к истечению
  показываются первыми (кому нужно внимание сегодня), а безлимитные и
  далеко оплаченные уходят в конец списка/на дальние страницы. Записи с
  нечитаемой датой всегда остаются в самом конце — в любом режиме.
  Реализовано так, что настройка читается из `settings.json` один раз за
  рендер списка, а не на каждую запись при сортировке.

## 🆕 v1.9 — управление группами: двунаправленно + разгруппировка + обратная привязка

- **Новый переключатель «Скрывать ведомых»** в «⚙️ Сортировка БД»
  (`bot/display.py`: `is_hide_followers_enabled`/`toggle_hide_followers`).
  Комбинируется с двумя уже существующими фильтрами.
  **Важно**: сами экраны управления связями (`leader_link.py`) НЕ проходят
  через этот фильтр — они используют `sorted_users_for_display()` вместо
  `prepare_users_for_display()`, иначе включённый фильтр прятал бы
  ведомых именно там, где их нужно видеть и редактировать.
- **«👑 Назначить ведущим» стало двунаправленным.** Раньше — только
  добавление, чекбоксы стартовали пустыми. Теперь при открытии экрана уже
  отмечены ✅ текущие ведомые; снятие галочки у уже привязанного —
  отвязывает его, отметка нового — привязывает. Всё одним подтверждением
  («✅ Готово»), без похода в два разных места. Кнопка переименовывается в
  «👑 Управление ведомыми», если у пользователя уже есть группа.
- **Новая кнопка «💔 Разгруппировать»** (только у тех, у кого уже есть
  ведомые) — открывает экран, где показана **только текущая группа**, а
  не общий список всех пользователей (то, о чём просили отдельно). Можно
  снять галочки у части ведомых и подтвердить, либо одним тапом «🔨
  Отвязать всех сразу» разорвать все связи разом.
- **Новая кнопка «🔗 Сделать ведомым»** — обратное направление: с карточки
  независимого пользователя выбираете, к какому из уже существующих
  ведущих его привязать (список показывает только ведущих —
  `core.db.get_leaders()`, а не всех подряд). Кнопка появляется только
  если в базе вообще есть хоть один ведущий — иначе список был бы пустым.
  Реализовано без FSM: username ведомого передаётся прямо в
  `callback_data` каждой кнопки (`followto:{follower}:{leader}`), поскольку
  это одиночный выбор, а не многошаговая форма.
- **`core/db.py`**: новая `get_leaders()` — все пользователи, у которых
  есть хотя бы один ведомый (используется и обратной привязкой, и
  проверкой «стоит ли вообще показывать кнопку "Сделать ведомым"»).
- Резюнк (`run_sync`) по-прежнему запускается только когда реально меняется
  членство в `credentials.toml` — привязка нового ведомого к
  просроченному/неактивному ведущему требует резюнка, отвязка — никогда
  не требует (ведомый просто остаётся с теми же значениями, что уже были,
  только теперь независимо).

## 🆕 v1.7 — клиентский бот для MAX

Новый пакет `max_bot/` — клиентский бот для мессенджера MAX (регистрация
по триалу, /status, /link, /pay, /help с инструкциями, приём чека с
пересылкой администратору в Telegram). Администрирование
(добавление/продление/удаление/рассылки) остаётся только в Telegram —
MAX-бот его не дублирует, это было явное решение при обсуждении.

- **Long Polling**, не Webhook — сознательный выбор для старта без
  дополнительной инфраструктуры (Webhook — то, что MAX рекомендует для
  продакшена, но требует отдельный поддомен + HTTPS-сертификат).
- **Общая база**: MAX-клиент — это обычная запись в `users.json` с
  `max_chat_id` вместо `telegram_id`. `core/db.py` получил
  `get_user_by_max_chat_id()`, `core/notify.py` — `send_max_message()` и
  `send_photo_bytes()` (синхронная отправка через сырой HTTP, тот же
  паттерн, что уже был для Telegram, для `services/cleanup.py` и
  `services/post_disable_reminders.py`, у которых нет event loop).
- **`bot/trial.py` → `core/trial.py`**: трекинг использованных триалов и
  генерация username/пароля никогда не были специфичны для Telegram —
  перенесены в `core/`, теперь общие для обоих ботов, один файл вместо
  дублирования логики.
- **Без FSM в MAX-боте** — сознательное упрощение (см. докстринг
  `max_bot/handlers/receipt.py`): вместо персистентного состояния для
  подтверждения чека используется короткий токен прямо в `callback_data`
  кнопки + недолгоживущий словарь в памяти процесса. Компромисс: если бот
  перезапустится между "прислали фото" и "нажали кнопку" — придётся
  прислать фото заново. Для MVP это приемлемо.
- **Одобрение чека от MAX-клиента** происходит теми же кнопками
  (➕1мес/➕2мес/✍️/❌), что и обычный чек из Telegram — админ ничего не
  делает по-другому, просто получает фото чека в тот же Telegram-чат.
- **`install.sh`/`deploy.sh`**: `MAX_BOT_TOKEN` — опциональный вопрос при
  установке (Enter — пропустить), юнит `trustpanel-max-bot.service`
  ставится/обновляется только если токен задан.

**⚠️ Честно про степень проверки:** библиотека `maxapi` не может быть
установлена и протестирована в среде, где это писалось (нет доступа в
интернет для `pip install`) — код построен по официальной документации
(`dev.max.ru/docs-api`, `love-apples.github.io/maxapi`) и по графу
импортов (собрана условная заглушка `maxapi`, весь `max_bot/` реально
импортируется без ошибок), но НЕ проверялся запуском против живого MAX.
Три конкретных места с максимальным риском неточности — в
`README.md` → раздел «MAX-бот (опционально)».

## 🆕 v1.6 — напоминания через +1/+3 дня после отключения

Отдельный демон/таймер (по требованию — не встроено в существующий
`cleanup`, а полностью отдельный юнит):

- **`services/post_disable_reminders.py`** + **`systemd/trustpanel-post-disable.service`**
  + **`systemd/trustpanel-post-disable.timer`** (ежедневно, 09:00 МСК —
  через час после `trustpanel-cleanup.timer`, чтобы отключения того же дня
  уже точно попали в базу).
- Логика: берём всех `status: "inactive"` с реальной `expires_at`, считаем
  `сегодня − expires_at` в днях. На +1 и +3 дня шлём напоминание с
  реквизитами, дальше не повторяем (трекается в новом поле
  `post_disable_notified`, том же паттерне, что и `notified_days`).
- `post_disable_notified` **не синхронизируется** между ведущим/ведомым
  (см. v1.5) — как и `notified_days`, это чисто история уведомлений
  конкретной записи, не часть общего доступа.
- Сбрасывается в `[]` при каждой реактивации (`extend.py`, `receipt.py`) —
  если клиент продлился, а потом снова просрочит в будущем, напоминания
  сработают заново, а не будут молча пропущены из-за старой отметки.
- `install.sh`/`deploy.sh` обновлены — новый юнит ставится/обновляется
  вместе с `cleanup`/`backup`.

## 🆕 v1.5 — связка «ведущий/ведомый» для мульти-девайс клиентов

Решает проблему: клиенты с несколькими логинами под разные устройства
(`SEvgeniy1-2`/`SEvgeniy3-4`, `STAndr1-2`/`3-4`/`5-6`/`7-8` и т.д.) держали
"ведомые" записи с `expires_at: null` вручную, чтобы не отключить лишнее
устройство раньше срока — но это значит, что при полном прекращении
оплаты эти записи так и оставались бы с VPN-доступом навсегда.

- **Новое поле `linked_to`** в записи пользователя (`core/db.py`) — если
  задано, это ведомый, поле указывает на username ведущего.
- **`update_user()` теперь единая точка синхронизации:** любое изменение
  `expires_at`/`status` для ведомого автоматически перенаправляется на
  ведущего, а затем то же значение проставляется всем его ведомым — в
  одной атомарной записи под тем же file-lock, что и раньше. Рассинхрон
  физически невозможен, так как ведомого нельзя продлить независимо ни
  из какого места кода (`extend.py`, `receipt.py`, `services/cleanup.py`
  — все идут через `update_user()`).
  `notified_days`/`telegram_id`/`pending_request` НЕ синхронизируются —
  у каждого устройства/члена семьи может быть свой Telegram и своя
  история уведомлений, общий только реальный доступ.
- **Удаление ведущего** автоматически отвязывает оставшихся ведомых
  (иначе `linked_to` указывал бы в никуда) — они остаются с последним
  синхронизированным значением как независимые записи.
- **UI:** в меню действий над пользователем — кнопка «👑 Назначить
  ведущим» (мульти-выбор ведомых из общего списка, постранично, как в
  рассылке) и «🔓 Отвязать» на карточке уже привязанного. Список
  кандидатов исключает тех, кто сам уже ведущий для кого-то (не даём
  строить цепочки ведущий→ведущий→ведомый — `update_user()` синхронизирует
  только один уровень вложенности).
- **Одноразовая миграция данных:** в текущей БД найдено и связано 5 групп
  (`SEvgeniy1-2`, `STAndr1-2`, `SMSergei`, `SMOleg`, `@Milden_79` — каждый
  как ведущий для своих `-2`/`-3`/`/2` вариантов). По вашему решению НЕ
  тронуты `kirill/kirillpc`, `aloxi/aloxipc`, `pelevin/pelevinm`,
  `Marcus2/Marcus3` — там не было однозначного кандидата в ведущие
  (оба варианта с `expires_at: null`), оставлены как есть.

## 🆕 v1.4 — bot.py разбит на пакет

`bot/bot.py` (~2900 строк, всё в одном файле) превратился в пакет `bot/`:
8 вспомогательных модулей (`config`, `states`, `keyboards`, `formatting`,
`pagination`, `display`, `trial`, `access`) + 14 файлов-хендлеров в
`bot/handlers/`, каждый со своим `aiogram.Router`. `bot/bot.py` теперь —
это только entrypoint (~55 строк): грузит `.env`, подключает роутеры,
запускает polling. Вся бизнес-логика не менялась ни на строчку — это
чисто механическое перемещение кода, см. ниже как это было проверено.

**Правило владения состояниями** (см. докстринг `bot/states.py`): каждое
FSM-состояние обрабатывается хендлерами ровно в одном файле. Если из
другого файла нужно ЗАЙТИ в чужое состояние (например, кнопка «✉️ Написать»
в меню действий пользователя, `list_users.py`, включает
`AdminMessage.personal`, а обрабатывает его уже `feedback.py`) — это
нормально и явно прокомментировано в докстринге каждого такого места.
Из-за этого правила порядок `dp.include_router(...)` в `bot/bot.py` не
влияет на поведение — у каждого `callback_data` и каждого состояния
ровно один владелец, коллизий по построению быть не может.

**Как проверено, что ничего не потерялось и не сломалось** (без доступа к
живому Telegram):
- Написана минимальная заглушка `aiogram` (Bot/Dispatcher/Router/F/types/
  FSM), пакет `bot.bot` реально импортирован через неё — поймано и
  исправлено 2 реальные ошибки (не хватало импорта `AddUser`/`AddUserMulti`
  в `add_user.py`; `F.from_user.id` требовал more permissive `__getattr__`
  в заглушке, что заодно подтвердило, что все `F.from_user.id != ADMIN_ID`
  фильтры в коде синтаксически рабочие).
- Точное сравнение (`diff`) списков `F.data == "..."`, `F.data.startswith("...")`
  и `F.text == "..."` между старой версией `bot.py` и новым пакетом —
  **побайтово идентичны** (34 / 25 / 15 совпадений соответственно).
- Подсчёт `@dp.message`/`@dp.callback_query` в старом файле против
  `@router.message`/`@router.callback_query` в новом пакете — **95 msg +
  59 callback в обоих случаях**, ни один хендлер не потерян и не
  задублирован.
- `tests/test_dates.py` (17 тестов) прогнаны заново на итоговом коде.

**Побочные мелкие улучшения по ходу переноса:**
- `_load_trial_used_ids`/`_save_trial_used_ids` (были в `bot.py`) переехали
  в `bot/trial.py` и переименованы в `load_trial_used_ids`/
  `save_trial_used_ids` без подчёркивания — раз они теперь используются из
  другого модуля (`handlers/database.py`), префикс "приватности" был бы
  вводящим в заблуждение.
- `extract_telegram_id_from_message()` (раньше жила рядом с `db_menu` в
  разделе "DATABASE MENU", хотя реально используется в
  `act_setid`-флоу из другого раздела) переехала в `bot/formatting.py` —
  туда, где она нужна по факту использования, а не по историческому
  соседству в старом файле.

    сайты/приложения в Bypass-список (чтобы Госуслуги, банки, VK, Ozon,
    Wildberries и т.д. работали при включённом TrustTunnel), с двумя кнопками

    Android и iOS — списки берутся из `core/instructions.py`, редактируются

## 🔴 Исправленные баги

- **`systemd/trustpanel-backup.timer`**: секция была буквально `Unit]` вместо `[Unit]` —
  невалидный INI/systemd-синтаксис. Исправлено на `[Unit]`.
- **`.env.example`**: отсутствовала `TRUSTTUNNEL_DOMAIN`, хотя `bot.py` требует её
  и падает с `RuntimeError` при старте без неё. Добавлена; заодно убраны
  `VPN_FILE`, `HOSTS_FILE`, `TRUSTTUNNEL_PATH` — они нигде в коде не читаются.
- **`services/users.py`**: удалён. Импортировал несуществующие
  `core.service.rebuild_credentials` и `trustpanel.generator.generate_tt_link` —
  модуль был нерабочим мёртвым кодом с устаревшей схемой данных, нигде не
  подключался из `bot.py`.
- **`bot/bot.py` — `manual_date()`**: голый `except:` (ловил абсолютно всё, включая
  `KeyboardInterrupt`) заменён на `except ValueError:`.
- **`bot/bot.py` — дублирующийся `extend_menu` (callback `"extend:"`)**: удалён.
  Был помечен в комментарии как "OLD, kept as-is" и физически недостижим — ни одна
  клавиатура не генерирует `callback_data="extend:..."` (везде используется
  `act_extend:...`, который матчится другим хендлером).
- **`systemd/trustpanel-bot.service` vs `install.sh`**: в оригинале это были ДВА
  разных, расходящихся определения одного юнита — install.sh генерировал свой
  hardened-вариант через heredoc, а закоммиченный в репо файл был другим и никогда
  не устанавливался. Теперь единственный источник правды — файл в `systemd/`,
  и `install.sh`/`deploy.sh` оба ставят именно его.

## 🟠 Устранённые риски

- **Race condition в `core/db.py`**: `load()` → изменить → `save()` без блокировки
  мог терять изменения при параллельных вызовах (админ продлевает + cleanup.py
  отключает одновременно). Добавлен `FileLock` (уже была зависимость проекта).
- **Самодельный TOML-парсер в `core/credentials.py`**: построчный `startswith()`
  заменён на `toml.load`/`toml.dump`. Раньше любое изменение формата файла
  тихо ломало парсинг без ошибки.
- **Три расходящихся реализации парсинга дат** (`bot.py`, `credentials.py`,
  `cleanup.py`) объединены в `core/dates.py`. Разница в поведении на "битых"
  датах могла привести к тому, что один модуль считает пользователя истёкшим,
  а другой — нет. Все бизнес-фиксы ("продление от текущей даты истечения",
  "календарные месяцы вместо +30 дней") задокументированы и покрыты тестами
  один раз, а не поддерживаются в трёх копиях.
  - **Важный нюанс**: `core/credentials.py` намеренно НЕ использует общий
    permissive `is_expired()` для решения, кому давать доступ к VPN — там
    оставлено строгое "fail closed" поведение оригинала (битая дата = не
    выдавать доступ), тогда как для отображения в списках битая дата
    трактуется как "не помечать истёкшим", чтобы не пугать админа глюком
    данных. Это то же поведение, что было в оригинале, просто теперь явно
    прокомментировано, а не разное по факту молчаливого разнобоя.
- **Права доступа к секретам**: `users.json`, `credentials.toml` и файлы бэкапов
  теперь получают `chmod 600` при каждой записи (раньше — только `.env` в
  `install.sh`, права на сами файлы БД никак не выставлялись).
- **`print()` → `logging`**: `core/service.py`, `core/notify.py`,
  `core/generator.py`, `services/cleanup.py`, `services/backup.py`.
  Уровни (`LOG_LEVEL` в `.env`), единый формат с таймстампом, `aiogram`
  прижат к `WARNING` по умолчанию, чтобы не шуметь.
- **`db_import_apply` (загрузка бэкапа через бота)**: раньше проверялся только
  валидный JSON-синтаксис (`json.loads`), что пропустило бы, например,
  `{}` или список без username-полей и молча убило бы БД. Теперь для
  `users.json` дополнительно проверяется форма: список словарей с непустым
  `username` у каждого.
